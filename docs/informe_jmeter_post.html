2. Plan de pruebas

Objetivo

Verificar el establecimiento y ciclo básico del WebSocket y observar latencia y errores cuando aumenta la concurrencia.

Sistema bajo pruebaServicio de chat del proyecto MPC Club de Ciencia
Rutaws://127.0.0.1:8000/ws/chat (la captura de JMeter muestra el host local y el puerto 8000)
ProtocoloWebSocket; el establecimiento se identifica con respuesta HTTP 101 Switching Protocols
Secuencia de samplersWebSocket Open Connection, Single Write, Single Read y Close
HerramientaApache JMeter 5.6.3
ListenersAggregate Report y View Results Tree

Tipos de prueba

  • Smoke: 1 hilo y una iteración para confirmar la conexión y ejecutar el ciclo mínimo.
  • Carga: 50 hilos concurrentes para observar el comportamiento del ciclo WebSocket.
  • Estrés: 500 hilos para exponer degradación y fallos bajo una concurrencia alta.
Criterio de lectura: el agregado incluye cuatro samplers por ciclo. Por eso, 4, 200 y 20,000 muestras no deben leerse automáticamente como el mismo número de mensajes de usuario procesados.

Fuente de resultados y capturas: docs/capturas_post. El árbol de resultados disponible es de smoke; las capturas de carga y estrés suministradas son de Aggregate Report.

6. Análisis final

Smoke

Con 1 hilo, 1 segundo de ramp-up y 1 iteración, el ciclo WebSocket básico se completó sin errores. La respuesta 101 confirma el establecimiento de la conexión; esta prueba verifica funcionamiento, no capacidad.

Carga

La corrida de 50 hilos registró 200 resultados de samplers y 0 % de errores. La latencia agregada fue baja en la muestra tomada. Al no verse el ramp-up ni la duración del grupo, no permite certificar comportamiento sostenido ni extrapolar a cargas mayores.

Estrés

Con 500 hilos se registraron 20,000 muestras y 72.32 % de errores. Los percentiles p95 y p99 de 5,947 ms y 7,515 ms reflejan degradación significativa. El resultado sugiere que esta configuración excede la capacidad estable del entorno ensayado, pero las capturas por sí solas no determinan si el origen es el servidor, el cliente de prueba o una dependencia.

Conclusión: la secuencia WebSocket funciona en smoke y la corrida de carga observada no presenta errores; la corrida de estrés revela fallos numerosos y latencias altas. Se recomienda repetir la prueba de estrés con JMeter no-GUI, ramp-up y duración registrados, y recoger métricas del servidor y causas de error por sampler.

Recomendaciones

1. Guardar el plan JMeter (.jmx) y el resultado (.jtl) de cada ejecución junto con las capturas.
2. Registrar usuarios, ramp-up, duración, loop count y configuración de cada sampler en los resultados.
3. En carga y estrés, conservar el View Results Tree o un reporte de errores con código/mensaje y correlacionarlo con los logs del backend.
4. Ejecutar pruebas escalonadas de concurrencia y monitorizar CPU, memoria, conexiones y dependencias del chat.

Nota de alcance: este documento refleja las capturas de WebSocket en docs/capturas_post. No representa pruebas del endpoint HTTP POST /api/chat.
