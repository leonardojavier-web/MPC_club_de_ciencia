1. Resumen ejecutivo

Este informe organiza la evidencia disponible de Apache JMeter para tres tipos de prueba: smoke, carga y estrés. El objetivo es comprobar la respuesta del servicio y observar cómo cambian los tiempos y los errores al aumentar el volumen de solicitudes.

Alcance de la evidencia: Smoke se ejecuta con 1 usuario, ramp-up de 1 segundo y 1 iteración para comprobar que el servicio funciona. En las capturas de resultados agregados de carga y estrés no se distingue con fiabilidad el ramp-up. En carga, 50 muestras se informan como volumen observado; para estrés, 30,000 muestras / 10,000 hilos equivale aproximadamente a 3 solicitudes por hilo si el plan ejecutó un sampler por iteración. Esta inferencia no sustituye la configuración original del Thread Group.

2. Plan de pruebas

Objetivo

Validar la disponibilidad del endpoint de consulta y medir latencia, percentiles, throughput y porcentaje de errores en tres niveles de exigencia.

Alcance técnico

Sistema bajo pruebaAPI backend del proyecto MPC Club de Ciencia
Rutahttp://127.0.0.1:8000/api/fundacion
MétodoHTTP GET
Respuesta esperadaRegistros de la fundación en formato JSON
Herramienta / versiónApache JMeter 5.6.3 (visible en las capturas)
Listeners solicitadosAggregate Report (Informe agregado) y View Results Tree (Árbol de resultados)

Tipos de prueba incluidos

  • Smoke: ejecución breve para verificar que la ruta responde correctamente.
  • Carga: concurrencia moderada para observar el comportamiento con solicitudes simultáneas.
  • Estrés: incremento extremo de hilos para identificar degradación y fallos bajo presión.
Condición de aceptación sugerida: respuesta HTTP válida y 0 % de errores en smoke; para carga, mantener errores en 0 % y latencia estable. En estrés se busca identificar el punto de degradación; no se considera una condición de operación normal.

Las capturas de evidencia están guardadas en docs/capturas_GET. Los datos numéricos que no se visualizan claramente en la evidencia se reportan como “no verificable” en lugar de asumir valores.

6. Análisis final

Smoke

El endpoint respondió correctamente en la muestra registrada: 1 usuario, 1 iteración y 0 % de errores. La duración de 269 ms permite confirmar la respuesta funcional básica en el entorno y momento capturados; no pretende medir capacidad concurrente.

Carga

Con 50 muestras, el informe agregado no registra errores y presenta una media de 4 ms. Es un resultado favorable para el volumen medido. No permite, por sí solo, afirmar capacidad para una carga sostenida mayor: la duración, el ramp-up real, la configuración exacta del grupo de hilos y las condiciones del equipo no son verificables en las capturas.

Estrés

La corrida de 10,000 hilos alcanzó 30,000 muestras, pero registró un 51.25 % de errores y un p95 de 2,262 ms. Esto indica que el sistema no sostuvo esa carga extrema de forma confiable. El throughput de 1,304.9 solicitudes/s debe leerse con cautela debido a la elevada tasa de fallos. La evidencia no basta para atribuir la causa a un componente concreto (API, dependencias, servidor de prueba o entorno).

Conclusión global

Conclusión: el servicio muestra un comportamiento adecuado en las corridas smoke y carga documentadas, pero presenta una degradación significativa bajo estrés extremo. No se recomienda usar el resultado de estrés como capacidad de producción sin repetir la prueba con configuración controlada, criterios de éxito explícitos y métricas del servidor.

Recomendaciones

1. Guardar el plan JMeter (.jmx) y los resultados (.jtl) junto con las capturas para hacer reproducibles las pruebas.
2. Registrar y documentar hilos, ramp-up, duración y loop count de cada Thread Group; repetir pruebas separadas para smoke, carga y estrés.
3. Ejecutar carga progresiva (por ejemplo, escalones de concurrencia) y repetir cada escalón para encontrar el umbral de degradación.
4. Correlacionar errores de JMeter con códigos HTTP, logs de backend, CPU, memoria, conexiones y dependencias externas.
5. En ejecuciones de alta concurrencia, usar JMeter en modo no-GUI y evitar listeners pesados durante la medición; generar el informe HTML desde el archivo JTL después de la corrida.
Fuente: capturas JMeter proporcionadas en docs/capturas_GET. Los resultados describen únicamente las ejecuciones evidenciadas y no constituyen una garantía de rendimiento en otros entornos.
